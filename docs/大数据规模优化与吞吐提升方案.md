# 大数据规模优化与吞吐提升方案

> 目标读者：后续接手本模块的开发/部署者。
> 本文所有数字均为本机实测（Windows，Python 3.13 venv，Polars 1.44.2，pyarrow + zstd），
> 复现脚本：`backend/scripts/bench_ingest.py`（在 `backend/` 下运行）。

---

## 1. 问题定位

平台定位是「大数据分析处理」，但一道隐性的墙把数据规模卡在了 100 MB 附近。

### 1.1 表面症状：一个硬编码常量

| 位置 | 原值 | 问题 |
| --- | --- | --- |
| `backend/app/services/file_service.py` | `MAX_UPLOAD_SIZE = 100 * 1024 * 1024` | 后端硬编码，改需动代码 |
| `frontend/src/api/files.ts` | `export const FILE_MAX_SIZE = 100 * 1024 * 1024` | 前端另存一份，两边可能漂移 |

但这只是**症状**。即便把 100 MB 改成 10 GB，问题也不会消失，只是把「一上传就报 422」
变成「一上传就把进程 OOM 掉」。

### 1.2 真正的瓶颈：一次入库要经历三次全量常驻内存

改造前，一份文件进到数据集版本里的链路是：

```
上传流 ──► FileService.read()          整个文件的 bytes 常驻          （第 1 份）
       ──► REGISTRY.load(data=content) 完整 DataFrame 常驻            （第 2 份，通常比文件更大）
       ──► create_version(df)          io.BytesIO() 里再攒一份 Parquet（第 3 份）
```

CSV 更糟：`utf-8` 解码出来是一个 `str`，再 encode 回 `bytes`，峰值可达文件体积的数倍。

结论：**上传上限 = 进程可用内存**。硬编码 100 MB 只是把这个 OOM 提前变成了一个错误码。

### 1.3 附带发现：读路径同样没有下推

读取版本快照走 `storage.read()` → 整个 Parquet 的 `bytes` → `pl.read_parquet`。
「只要 3 列」也要把全表解码一遍。

## 2. 优化目标

| 维度 | 改造前 | 目标 | 实测结果 |
| --- | --- | --- | --- |
| 单文件上限 | 100 MB（硬编码） | 配置驱动，默认 2 GB，可调 | ✅ `MAX_UPLOAD_SIZE_BYTES`，默认 2 GB |
| 入库峰值内存 | 随文件**线性**增长（4M 行 = 849 MB） | 与文件体积**无关** | ✅ 翻倍数据内存倍率 **1.01×** |
| 大文件内存 | 4M 行 849 MB | 常数级、可预测 | ✅ 稳定在 **约 380 MB**（含 62 MB 库地基） |
| 读取下推 | 无（全表解码） | 列投影 + 谓词下推到扫描层 | ✅ 8M 行取 2 列/末 100 行：**35 ms vs 75 ms** |
| 上传/下载内存 | 全量 `bytes` | 分块流式 | ✅ 块大小恒定 |
| 吞吐 | 无明确指标 | 不劣化 | ⚠️ 见 §5 的取舍说明 |

**明确不做的事**：不引入 Spark/Flink 等外部计算引擎。目标是在单机单进程内，
把「内存成为规模瓶颈」这件事消掉，代价可控、无需新增部署组件。

## 3. 功能范围

### 3.1 配置化规模上限

新增（`app/core/config.py`）：

```python
MAX_UPLOAD_SIZE_BYTES = 2 * 1024 * 1024 * 1024   # 单文件上限
UPLOAD_CHUNK_SIZE_BYTES = 4 * 1024 * 1024        # 上传读块
INGEST_STREAMING_ENABLED = True                  # 可关闭流式做 A/B
INGEST_ROW_GROUP_ROWS = 262144                   # Parquet 行组行数
INGEST_SCHEMA_INFER_ROWS = 50000                 # schema 采样行数
INGEST_MAX_MATERIALIZE_BYTES = 1024**3           # 不可流式格式的物化上限
INGEST_CHUNK_BYTES = 32 * 1024 * 1024            # ★ 分块大小（规模上限的真正旋钮）
INGEST_STREAMING_THRESHOLD_BYTES = 256 * 1024**2 # ★ 快/有界 两条路径的分界
DATASET_LAZY_SCAN_ENABLED = True                 # 懒扫描读路径
```

前端不再硬编码，改为启动时向 `GET /api/v1/files/limits` 拉取。

### 3.2 存储层：零拷贝 + 原子落盘

- `StorageBackend.promote()`：把临时文件 `rename` 成最终 key（同盘 rename 是原子的），
  避免「DB 已提交、Storage 里还是半截文件」。
- `StorageService.local_path()` + `supports_local_path()`：本地后端直接给出真实路径，
  让上层能用 `scan_parquet` / `pyarrow` 走 mmap，而不是先读成 `bytes`。
  非本地后端返回 `None`，调用方据此降级（`DatasetService.version_local_path()` 统一处理）。
- `FileService.open_stream()`：按块迭代下载，响应不再把整个文件读进内存。

### 3.3 分块入库引擎（`app/data_engine/ingest.py`）

- **可流式**：CSV / TSV / TXT、NDJSON、Parquet、**稠密 ARFF**。
- **不可流式**：XLSX / XLS / 标准 JSON、**稀疏 ARFF** —— 底层库无流式接口，
  超过 `INGEST_MAX_MATERIALIZE_BYTES` 时**明确拒绝**并提示先转 CSV/Parquet，
  而不是把进程撑爆。
- **非 UTF-8 编码**（GBK/GB18030 等）：先增量转码为 UTF-8 临时文件再入库。

> ARFF 一开始被归在「不可流式」，代价很大：它的 `@data` 段其实就是逗号分隔文本，
> 但走物化路径时是**纯 Python 逐行逐格**解析（`fh.read()` → `splitlines()` →
> 每格一次 `_coerce`）。实测 385 MB / 1000 万行要让一个 HTTP 请求跑 **139.8 s**，
> 直接撞穿前端 60 s 超时（见 §4.6）。现已按「扫头部 + 流式解析数据段」改造，
> 降到 **5.6 s**。

### 3.4 连接器模块

见 [`docs/db-connector.md`](./db-connector.md)：通过外部数据库突破文件体积限制。

## 4. 关键实现要点

### 4.1 ★ 为什么必须自己分块：`sink_parquet` 并不真流式

最初的实现是教科书式的 `pl.scan_csv(...).sink_parquet(...)`，假设它是流式的。
写完之后做了一次验证，结果是反的：

| 4M 行 / 187 MB CSV | 峰值内存 |
| --- | --- |
| `scan_csv → sink_parquet`（号称流式） | 631 MB |
| `scan_csv → collect() → write_parquet`（完全物化） | 697 MB |
| `read_csv_batched` + `ParquetWriter` | 744 MB（更差：它先把整个文件读进缓冲） |

**流式只省了约 10%。** 继续在这条路上调参是没有意义的 —— 必须自己控制读取粒度。

### 4.2 分块设计

```
文件 ──► 按 INGEST_CHUNK_BYTES 切块（切点对齐到「引号外的换行」）
        ──► 首块推断 schema，后续块复用（保证类型一致）
        ──► 逐块解析 ──► 按行组粒度增量写 Parquet
```

三个必须处理的细节：

**① 引号感知的切点。** RFC 4180 允许字段值内含换行（只要整体被引号包裹）。
直接按 `\n` 切会把一条记录劈成两半。实现用 `bytes.rfind` + `bytes.count` 判断
「该换行处的引号数是否为偶数」：

```python
cut = buf.rfind(b"\n")
while cut >= 0 and (buf.count(quote, 0, cut) & 1):
    cut = buf.rfind(b"\n", 0, cut)
```

> 用 `bytes.count` 而不是逐字节循环：在 187 MB 上逐字节扫描要十几秒，
> `count` 在 C 层，整份文件只多花约 50 ms。

**② 首块采样决定全局 schema。** 首块推断出的类型会被后续所有块复用。
若采样到的全是整数、后面却出现 `待补`，解析会抛错 —— 此时降级为
「全字符串列导入」（`strategy=chunked-utf8`），保证「能进得来」优先于「类型最准」。

**③ 两条路径的行为必须完全一致。** 因为走哪条路由**文件体积**决定，
若对参差行的处理不同，就会出现「小文件能导入、大文件报错」这种极难排查的现象。
`truncate_ragged_lines` 在两条路径上保持同值，并有专门用例把这一不变量钉住
（`test_both_ingest_paths_agree_on_ragged_rows`）。

### 4.3 自适应路由：在「快」与「有界」之间取舍

实测两条路径是明确的权衡，没有一条能同时赢：

| 路径 | 边际吞吐 | 内存 |
| --- | --- | --- |
| `sink`（scan + sink_parquet） | ≈ **1050 MB/s** | ≈ 3× 文件体积，**线性增长** |
| `chunked`（自研分块） | ≈ **112 MB/s** | **恒定约 380 MB** |

因此按 `INGEST_STREAMING_THRESHOLD_BYTES`（默认 256 MB）分界：

- **装得下就走快的**（≤ 256 MB → sink）；
- **装不下就走有界的**（> 256 MB → chunked）。

两者互为兜底：任一路径失败都落到另一条，最后才是全字符串列降级。
压缩代价说明：`chunked` 慢在少了 Polars 的**并行压缩**（写 parquet 由 pyarrow
串行完成），不是解析慢。

### 4.4 读路径：懒扫描 + 下推

`DatasetService.scan_version()` 返回 `pl.LazyFrame`，列投影与谓词由 Polars 在
Parquet 扫描层完成。大版本走懒加载，小版本仍走「整表 + 缓存」，避免小数据
被懒执行的开销反噬。

### 4.5 ARFF 流式化：把「不可流式」改回可流式

ARFF 的 `@data` 段是**定宽的逗号分隔文本**（标称值用单引号包裹，缺失值是 `?`），
只要先扫一遍头部拿到 `@attribute` 定义，就能给它一个显式 schema 并按块解析 ——
这正好是分块引擎已经具备的能力。于是：

```
扫头部（逐行读到 @data，记录字节偏移 + 解析 @attribute）
   ──► 数据段按 INGEST_CHUNK_BYTES 分块
   ──► pl.read_csv(schema=头部给定的 schema, quote_char="'", null_values=["?"])
   ──► 增量写 Parquet 行组
```

实现要点：

1. **头部必须逐行读，不能 `fh.read()`。** 头部只有几十行，但文件可能几百 MB ——
   任何一次性读取都会让内存重新与文件体积挂钩，那正是本模块要消灭的东西。
   用 `for raw in fh` + `fh.tell()` 拿到数据段起始字节偏移。
2. **schema 显式给定 ⇒ 不推断 ⇒ 跨块类型恒定。** 这是分块路径本来就依赖的性质。
3. **`?` 必须声明为 null。** 否则 `numeric` 列遇到缺失值会解析失败。
4. **稀疏表示（`{idx val, ...}`）不是定宽列**，直接退回整体物化。
5. ★ **任何异常都退回整体物化。** 这是最重要的一条：物化是改造前就存在、
   已被测试覆盖的语义，用它兜底可保证「同一个文件无论走哪条路，结果一致」。
   这条不变量由 `test_arff_streaming_matches_materialized` 钉住 ——
   若两条路径结果不同，就会出现「同一个文件今天导入和明天导入不一样」这种
   最难排查的问题。

实测（同一文件 `airlines_train_regression_10000000.arff`，385 MB / 1000 万行 × 10 列）：

| 路径 | 耗时 | 说明 |
| --- | --- | --- |
| 改造前（整体物化，纯 Python 逐格解析） | **139.8 s** | 生产请求日志实测 |
| 改造后（头部扫描 + 分块流式，`chunked-arff`） | **5.6 s** | 25× 加速，68.5 MB/s |

峰值内存：地基（仅 import polars+pyarrow）71.0 MB，入库过程 470.4 MB
⇒ 数据相关约 **399 MB**，与 CSV 分块路径的 ~380 MB 同一量级（**有界**）。
产出 Parquet 65.9 MB（源文件的 5.8×）。

### 4.6 ★ 长耗时入库与 HTTP 超时：一个会让「成功」看起来像「失败」的坑

这是把上面两件事串起来的真实事故：

- 后端 `POST /datasets` 在**请求内同步完成入库**，ARFF 大文件耗时 139.8 s；
- 前端 axios 全局兜底超时是 **60 s**；
- 于是请求在前端被判定失败，**但服务端其实已经成功**（HTTP 200、数据已落盘）；
- 用户看到 timeout 后自然重试 ⇒ **又建了一份完全相同的重复数据集**。

实测证据：库里出现**两个数据集**，`source_file_id` 都是同一个文件，
行数都是 10,000,000。也就是说「上传失败」实际成功了两次。

两条修正（缺一不可）：

1. **性能**：ARFF 流式化（§4.5）把 139.8 s 压到 5.6 s —— 治本。
2. **口径**：给长耗时端点单独放宽超时（`LONG_OPERATION_TIMEOUT_MS = 30 min`，
   覆盖 `POST /datasets`、`/files/upload`、`/connectors/{id}/import`），
   并把超时文案改成「服务端可能仍在处理，请稍后刷新确认，**不要立即重试**」
   —— 否则用户还是会在别的格式/更大的文件上重复同一个错误。

同时保留了**异步化**作为后续方向（见 §9）。

## 5. 实测基准

环境：Windows，Python 3.13 (venv)，Polars 1.44.2，zstd。
方法：**每条路径起独立子进程**，读该子进程自报的 `PeakWorkingSetSize`。
（同进程内比较会被「内存不归还」污染 —— `PeakWorkingSetSize` 是整进程生命周期峰值，
跑过别的阶段就再也降不下来。父进程轮询子进程工作集的做法实测不可靠，会稳定给出
约 10 MB 的假数字，故弃用。）

库地基（只 import polars + pyarrow，不碰数据）= **61.9 MB**。
下表「数据相关」= 峰值 − 地基。

### 5.1 峰值内存（数据相关，MB）

| 行数 | CSV 体积 | legacy（改造前） | sink | **chunked** |
| --- | --- | --- | --- | --- |
| 1,000,000 | 45.3 MB | 216.2 | 226.2 | 267.0 |
| 2,000,000 | 92.7 MB | 414.9 | 393.9 | 346.2 |
| 4,000,000 | 187.4 MB | 849.4 | 566.8 | **377.4** |
| 8,000,000 | 377.0 MB | （未测，会吃掉过多内存） | 850.3 | **380.5** |

**规模翻倍（4M → 8M）时的内存倍率：**

| 路径 | 数据相关内存 | 倍率 | 判定 |
| --- | --- | --- | --- |
| legacy | 216.2 → 849.4 MB（1M→4M） | ×3.93（规模 ×4） | 线性 ❌ |
| sink | 566.8 → 850.3 MB | **×1.50** | 线性 ❌ |
| **chunked** | 377.4 → 380.5 MB | **×1.01** | **有界 ✅** |

即：`chunked` 路径下，**数据量翻倍内存不变**。这是「突破 100 MB 上限」的核心证据 ——
上限不再由内存决定，而由磁盘决定。

### 5.2 耗时与吞吐

| 行数 | legacy | sink | chunked |
| --- | --- | --- | --- |
| 1,000,000 | 0.51 s | 0.74 s | 1.22 s |
| 2,000,000 | 0.63 s | 0.78 s | 1.62 s |
| 4,000,000 | 0.91 s | 0.93 s | 2.50 s |
| 8,000,000 | — | 1.11 s | 4.19 s |

上表是**端到端墙钟**，含进程启动 + 应用导入（约 0.6 s，与数据量无关）。
去掉固定开销后的**边际吞吐**才是可外推的数字：

- `sink`：(4.19 s − 0.93 s) / 189.6 MB ≈ **1050 MB/s**
- `chunked`：(4.19 s − 2.50 s) / 189.6 MB ≈ **112 MB/s**

> 报吞吐必须说明口径。只报端到端会把小文件的固定开销摊进分母，低估大文件性能；
> 只报边际吞吐则掩盖了小文件的启动成本。两者都给才是诚实的。

推算：`chunked` 处理 10 GB CSV（约 5.3 亿行）≈ **95 秒**，峰值内存仍约 380 MB。

### 5.3 读取下推（8M 行 / 5 列 Parquet）

| 操作 | 耗时 |
| --- | --- |
| 只取 2 列 + 取末 100 行（`scan_parquet` + `select` + `filter`） | **35.3 ms** |
| 全表物化读取 | 75.4 ms |

加速 2.1×。收益随「选取比例」下降而放大 —— 这里是取 2/5 列，若只取 1 列收益更大。

## 7. 顺带修掉的一个真实缺陷

在测 GBK 大文件时发现：`loaders._read_head()` 固定读前 64 000 字节，
而 `_detect_encoding` 直接 `data.decode("gb18030")`。**64 000 这个切点有约一半
概率落在汉字中间**（GBK 汉字占 2 字节），截断处必然抛 `UnicodeDecodeError`，
于是整份文件被判成 `latin-1` → 按 `utf8-lossy` 读 → **中文列名和内容全部乱码**。

关键在于它**只对超过 64 KB 的文件生效**：小文件测试完全发现不了，而「大文件」
正是本次要支持的对象 —— 不修的话，越大越容易踩。

修复：新增 `_decode_probe()`，解码失败时依次丢掉结尾 1~3 字节重试
（覆盖 UTF-8 与 GB18030 的 4 字节序列）。回归用例
`test_decode_probe_tolerates_truncated_multibyte_tail` 用**掐尾字节**的方式
确定性地构造截断（而不是指望文件长度恰好落在汉字中间 —— 第一版就是这么写的，
那份数据恰好对齐，用例变成了空转）。

## 8. ML 链路的内存治理（数据集 9 事故复盘）

§1~§7 解决的是「**存得下**」；这一节解决「**算得动**」。两者是同一件事的两半 ——
入库上限放开到 GB 级之后，第一件会撞上的墙就是 sklearn 的**稠密矩阵要求**。

### 8.1 症状

在 dataset 9（airlines，**10,000,000 行 × 10 列**）上创建 Experiment 并运行：

```
numpy._core._exceptions._ArrayMemoryError:
Unable to allocate 57.1 GiB for an array with shape (10000000, 767) and data type int64
```

`767` 是可疑点：源表只有 10 列。多出来的 757 列全部来自 **one-hot 展开**。

### 8.2 根因：五处「默认装得进内存」

| # | 位置 | 缺陷 |
| --- | --- | --- |
| ① | `preprocessing._make_pipe` | `OneHotEncoder` 不设 `max_categories`。`Origin`(369) / `Dest`(368) / `UniqueCarrier`(30) 三类标称列展开成 767 列 |
| ② | `preprocessing.fit/transform` | 物化前无规模预检，直接 `to_numpy()` |
| ③ | `preprocessing._matrix_to_frame` | `{name: arr[:, i].tolist()}` 造出 **行×列个 Python 对象**（767 × 1000 万 ≈ 76.7 亿），比矩阵本身更致命 |
| ④ | `evaluation.evaluate_clustering` | 轮廓系数 O(n²)，在 1000 万行上既算不下也算不完 |
| ⑤ | 推理侧（`experiments.service.predict`、`step_runner.run_predict_step`、`workflow.runners.ml_predict`） | 训练侧可以抽样，**推理不能抽样**（少一行就是少一行结果），同样一次性稠密化 |

外加两个放大器：
- `step_runner.run_preprocess_step` 为了一个 5 行预览去 transform 全量数据；
- `ExperimentService._execute` 在抽样之后仍持有整表 `df`（1000 万行 × 10 列 ≈ 1.3 GB），
  与预处理矩阵的峰值叠加。

### 8.3 反事实：767 列是怎么来的

实测（`backend/scripts/bench_ml_memory.py cluster`，dataset 9 真实 Parquet）：

| 标称列 | 取值数 |
| --- | --- |
| `UniqueCarrier` | 30 |
| `Origin` | 369 |
| `Dest` | 368 |

不做基数控制时，one-hot 展开后的宽度 = 6（数值）+ 30 + 369 + 368 = **774 列**，
1000 万行 × 774 列 × 8 B = **57.7 GiB** —— 与报错里的 57.1 GiB / 767 列**完全对得上**
（差 7 列是那次运行把它当目标列排除后的结果）。这就确认了根因判断，而不是猜的。

### 8.4 三层治理（缺一不可）

```
① 抽样  cap_training_rows()          —— 让默认跑得动，且绝不静默
② 控基数 ML_ONEHOT_MAX_CATEGORIES     —— 从源头压住列数膨胀
③ 预检  _assert_dense_fits()          —— 真装不下时给可操作的中文报错
   分块  ml_engine/inference.py        —— 推理不能抽样，只能分块
```

配置（`app/core/config.py`）：

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `ML_MAX_TRAIN_ROWS` | 200,000 | 单次训练最大样本数，超出即随机抽样（<=0 关闭） |
| `ML_MAX_DENSE_BYTES` | 2 GiB | 稠密矩阵内存预算（<=0 关闭预检与分块） |
| `ML_ONEHOT_MAX_CATEGORIES` | 50 | one-hot 单列最大类别数，低频合并为「其他」（<=0 不合并） |
| `ML_MAX_SILHOUETTE_SAMPLES` | 20,000 | 轮廓系数采样上限（该指标 O(n²)） |

**抽样必须有回执。** `cap_training_rows` 返回 `{sampled, original_rows, used_rows, sample_rate}`，
由调用方写进 `run.artifacts["sampling"]` 并 `emit("sample", ...)`。
静默改训练集规模会让指标无法解释 —— 用户会以为模型是在全量数据上训的。

**抽样必须先于切分与预处理。** 顺序错了等于没做：1000 万行会先被
`ColumnTransformer` 展开成稠密矩阵，抽样的意义就没了。

### 8.5 分块推理：语义无损的替代方案

`app/ml_engine/inference.py` 提供 `batch_predict` / `batch_predict_proba` /
`batch_transform` / `batch_evaluate`。要点：

- 块大小 = `ML_MAX_DENSE_BYTES / (列数 × 8 × 4)`。**4 倍安全系数**是因为同一时刻
  同时存在「原始列数组 + transform 输出 + ColumnTransformer 的 column_stack 中间体 +
  估计器内部副本」，只按单个矩阵估算必然低估。
- 估算仍偏乐观时**自动折半重试**（同一块，不是跳过），且只对
  `MLEngineException` / `MemoryError` 重试 —— 业务错误重试是掩盖问题。
- **逐元素等价**：`estimator.predict` 是逐样本前向计算，块间无依赖。
  探针与回归用例都断言 `chunked.equals(reference)`，而不是「差不多」。
- `batch_evaluate` 只把「产生预测」分块；指标是全局量，仍在完整序列上算一次。

### 8.6 实测（dataset 9 真实数据，独立子进程自报 `PeakWorkingSetSize`）

库地基（import polars + sklearn，不碰数据）= **131.3 MB**。

| 链路 | 治理前 | 治理后 | 说明 |
| --- | --- | --- | --- |
| 聚类（kmeans 8 簇） | 崩溃（57.7 GiB 申请） | **2,575.0 MB**，6.0 s | 抽样 200,000 行（2%），one-hot 137 列 |
| 回归（`DepDelay`，RF-30） | 崩溃 | **1,611.3 MB**，~96 s | 训练 160,000 / 测试 40,000 行 |

聚类链路的峰值构成（分段实测）：

| 阶段 | 累计峰值 |
| --- | --- |
| 读完 1000 万行 Parquet | 1,269.2 MB |
| 抽样到 20 万行 | 1,269.2 MB（抽样本身不增峰值） |
| 预处理（20 万 × 137 稠密矩阵） | 1,718.9 MB |
| kmeans 拟合 | 1,718.9 MB |
| 轮廓系数（2 万行子样本，O(n²)） | 2,781.0 MB |

释放整表 `df` 前后（同机同数据）：聚类 3,739.8 → **2,575.0 MB**（−31%），
回归 2,059.0 → **1,611.3 MB**（−22%）。

### 8.7 排查中发现的三个附带缺陷

1. **`ml.evaluate` 一接预处理就必然失败**（真实缺陷，已修）。
   它取 `model.feature_names_` 当原始列名用 —— 而那训练后是 **one-hot 之后的列名**
   （如 `cat_hi=c1`）。拿去 `df` 里挑列，非数值列全被过滤掉，紧接着
   `pipeline.transform` 报 `transform 缺失训练列: ['cat_hi', 'cat_lo']`。
   也就是说：**工作流里 `ml.train → ml.evaluate` 这条链本来就跑不通**。
   修法与 `ml.predict` 对齐：先问节点 `config.feature_columns`，再问上游训练节点的输出。
   既有测试没有覆盖「带预处理 + ml.evaluate」的组合，所以一直没被发现。

2. **`_assert_dense_fits` 的尺寸格式化会显示「0.0 GiB」**。原实现一律
   `needed / 1024**3`，预算 64 MB 时渲染成「0.0 GiB」—— 而这条提示存在的唯一意义
   就是让用户知道「差多少」，显示 0.0 等于没提示。改为 `_human_bytes()` 自动选单位。

3. **`arr[:, i].tolist()` 的装箱开销**（见 §8.2 ③）。改用
   `pl.from_numpy(np.ascontiguousarray(arr), schema=names)` 按缓冲区构造，不逐元素装箱。

### 8.8 验收指标（ML 部分）

见 §6 表格末段的「ML 链路内存治理」区块；测试文件
`backend/tests/test_ml_memory_governance.py`（34 项）。

> 与 §6 的取舍一致：**不断言具体内存 MB 数**（跨平台/跨版本的噪声会把它变成 flaky），
> 改为断言**不变量** —— 「分块结果逐元素等于一次性结果」「超预算必抛可读错误」
> 「抽样必须带回执」「抽样后输出行数不减少」。真实内存数字留在本节表格里。

## 9. 已知限制与后续方向

1. **`chunked` 吞吐是取舍，不是最优。** 112 MB/s 的瓶颈是 pyarrow 串行压缩。
   可探索的方向：多线程并行压缩不同行组后合并；或在内存充裕的部署上直接调高
   `INGEST_STREAMING_THRESHOLD_BYTES`（例如 2 GB）走快路径。
2. **NDJSON 目前复用分块路径**，但每行独立、无需引号感知，理论上可以用更轻的切块。
3. **`read_csv_batched` 不可用**（实测先把整份文件读进缓冲，比物化更差）——
   不要再尝试用它做流式。
4. **退化为全字符串列时会重复转码一次。** `_prepare_csv_source()` 在「分类型尝试」
   与「全字符串重试」中各被调用一次，因此非 UTF-8 且**类型冲突**的文件会多走一遍
   转码（同目录、同文件名，结果正确但白做一次 I/O）。只在降级路径上发生，
   大文件场景建议先把源转成 UTF-8 再上传。
5. **XLSX 仍然是硬上限。** 它本质是 zip 容器，理论可行但需引入 `openpyxl`
   只读模式逐行迭代，收益与成本待评估。（ARFF 已不再是 —— 见 §4.5。）
6. **连接器抽取同样依赖批大小**（`CONNECTOR_BATCH_ROWS`，默认 5 万行）——
   见 [`db-connector.md`](./db-connector.md) §4.2。
7. **入库仍是同步请求，未异步化。** 目前靠「流式化把耗时压下来 + 放宽超时口径」
   兜住（§4.6）。真正的解法是提交后台任务 + 轮询进度，这样无论多慢都不会
   牵住 HTTP 连接，也能给用户真实的进度条。这是下一步该做的事。
8. **抽样是有损的，且默认只训 20 万行。** 这是「默认跑得动」与「指标可解释」的取舍：
   想要全量训练就把 `ML_MAX_TRAIN_ROWS` 调大（同时调大 `ML_MAX_DENSE_BYTES`），
   但必须自行保证内存。**平台不该替用户静默决定**，所以抽样信息一路写到
   `run.artifacts["sampling"]` 与前端进度事件里。
9. **决策阈值的曲线/位移计算仍是逐样本 Python 循环。** `threshold.py` 的
   `apply_threshold` / `label_shift_ratio` / `threshold_curve` 都对概率列做
   `to_list()` 后循环（曲线还要扫 19 个阈值档位）。在 1000 万行上是「慢」而不是「崩」，
   且只在用户**显式传 threshold** 时触发，因此本轮未改。要做的话方向是先在
   概率列上做 polars 向量化分桶，或对曲线基数据按 `ML_MAX_SILHOUETTE_SAMPLES`
   同口径抽样。
10. **模型训练本身仍是单机内存内。** 分块只解决了「物化」，没解决
    `estimator.fit` 对全部样本的需求（sklearn 没有 out-of-core 训练）。
    真要训 1000 万行，出路是这批数据落到增量学习/分布式框架上，而不是继续调预算。

## 10. 报告与建模链路的缺陷修复（Agent 报告事故复盘）

§8 让 1000 万行**跑得动**；这一节复盘的是紧接着发生的事 ——
用户下载到的那份 `航空公司出发延误预测分析与建模报告.md`（1.36 MB）
与 AI 实验室对话，暴露出 6 个与规模无关、但同样致命的缺陷。

> 证据来源有两处，都可在本机复现：
> ① 用户下载的报告原文（含 11 张内联 SVG）；
> ② `backend/data/xiaoluo.db` 里 dataset 9 的 experiment 24~30 / run 24~30
>    （含 3 次 `target_column 不能出现在 excluded_columns 中`、1 次 57.1 GiB 崩溃、
>    2 次 kmeans 成功）。全部结论由 `sqlite3` 查询与无 LLM 探针脚本得出。

### 10.1 章节号「一 / 二 / 三 / 六」：硬编码序号 + 缺失章无说明

`ReportGenerator` 里写死「一、数据概览 … 四、建模与评估」，三个导出器里又各自写死
「五、关联实验」「六、结论」。当某一章因为缺少上游结果而没生成时，序号不会顺延，
也**没有任何说明** —— 读者无法分辨「这章确实没有」还是「编号写错了」。

修复：新增 `app/reports/numbering.py`，把章节计划收敛到唯一一处：

| 能力 | 作用 |
| --- | --- |
| `chapter_heading(key)` | 生成器与三个导出器共用「序号 + 标题」，杜绝跨格式不一致 |
| `strip_section_number(heading)` | 去掉任意来源标题的序号前缀（LLM 叙述常自带「一、」） |
| `chapter_status(obj)` | 算出每章是否生成、未生成的可操作原因 |
| `refresh_chapter_status(obj)` | LLM 叙述补齐章节后重算状态（否则报告同时出现该章正文与「该章未生成」） |

序号保留在固定计划表上（缺四、五时结论仍是「六、」），缺口处插入**未生成章节说明**
区块，逐条给出原因（例如「未执行 ml.train / ml.evaluate，也没有可用的
Experiment / Run」）。附带修掉一个撞号隐患：LLM 新增的章节标题一律剥掉序号，
避免「四、建模建议」与计划表的「四、建模与评估」重号。

### 10.2 报告里没有「建模与评估」章：两条入口的能力不对齐

`POST /reports/generate` 会自动发现该数据集最新的 Experiment/Run 并写入 `ml=` /
`experiments=`；而 Agent 工具 `report.generate` **从来没有传过这两个参数**。
于是用户在 AI 实验室里说「选择适合的机器学习模型进行处理」，拿到的报告里
完全没有建模章节 —— 10.1 那个跳号恰好是这件事的外显症状。

修复：把发现逻辑抽成 `app/reports/discovery.py::discover_ml_context()`，
两条入口共用；并把「预测目标列 / 训练集抽样 / 运行状态」一并写进建模章
（回归任务里目标列一旦被误判，读者只看指标数字是发现不了的）。
未生成时把原因回执给 Agent（`missing_chapters`），否则 Agent 会向用户宣称
报告已涵盖建模。

### 10.3 ★ 「Month 正态性 Q-Q 图」357 KB：分类列判定漏掉浮点编码列

`is_categorical_like` 只有 `dtype.is_integer()` 分支，而 ARFF / CSV 里的日历字段
常被读成 **Float64**：

```
Month       Float64  n_unique=12    → 旧：连续量   新：分类
DayofMonth  Float64  n_unique=31    → 旧：连续量   新：分类
DayOfWeek   Float64  n_unique=7     → 旧：连续量   新：分类
```

后果有三个，都能在事故报告里直接看到：这三个列进了相关性热力图、被算了均值、
还各生成了一张正态 Q-Q 图（`Month` 那张 357 KB，纯属伪影）。

修复：`app/analysis.py` 新增 `classify_columns()` ——

1. 浮点列在「唯一值 ≤ 50 且唯一值远少于行数」且**取值全是整数**时判为分类编码；
2. 判定只对 **行数 ≥ 1000** 的表生效（`_FLOAT_CATEGORICAL_MIN_ROWS`）：
   31 行的表里「7 个取值」只说明采样少，不说明它是编码列。加这道闸门是为了
   让改动只作用于它要解决的大表场景，不牺牲小数据集上原有的图表完整性；
3. 顺带把「逐列 n_unique」改成**一次 `select` 批量算**：原实现里
   `categorical_columns()` + `continuous_columns()` 会把每列的唯一值数算两遍。

### 10.5 质量问题表：三个列全是错的

事故报告里的「质量问题明细」长这样：

```
| 位置      | 类型 | 说明                                              |
| None      | -    | 按 整行 检测到 3799 行重复 (0.04%)                 |
| DepDelay  | -    | 字段 'DepDelay' 检测到 1347955 个异常值 (13.48%)… |
```

`QualityIssue` 的字段是 `check / severity / message / column / details`，
而渲染器读的是 `type` ⇒ 「类型」列全 `-`；`column=None` 被直接 `str()` 成 `"None"`；
严重度（low/medium/high）根本不展示；「其他质量指标」表只剩下一个 `has_errors`，
因为 `statistics` / `recommendations` 被「排除 dict/list」的兜底逻辑整段丢掉。

更严重的是**口径误导**：`DepDelay` 的 13.48% 离群是按 IQR 边界 `[-16.5, 19.5]`
判出来的，报告以 `severity=high` 呈现，读者会以为数据脏 ——
而那批记录就是「延误」本身的右偏长尾，按这个口径清洗会把待预测现象整段删掉。

修复：列改为 `位置 / 类型 / 严重度 / 说明`（`column=None` → 「全表」，
`check` 映射中文标签）；`statistics` 渲染成「质量统计口径」表、
`recommendations` 渲染成「质量修复建议」表；离群比例 ≥ 10% 时补一条口径说明
（「IQR 边界在此不适用，这部分是分布本身的尾部，不等于录入错误」），
该列正好是建模目标列时再加一句「其长尾就是待预测现象本身，不应删除」；
自动结论也从「建议在建模前清洗」改为按「真正需要处理的问题数」措辞。

### 10.6 ★ 「选择适合的模型」被做成了聚类：任务推断 + 冗余参数两道门

一次「选择适合的机器学习模型进行处理」的完整链路，在数据库里留下了完整痕迹：

| experiment | task | model | target_column | run 结果 |
| --- | --- | --- | --- | --- |
| 26 | classification | logistic_regression | DepDelay | failed（0.19 s，见下） |
| 27 | regression | linear_regression | DepDelay | failed（0.20 s，见下） |
| 28 | clustering | kmeans | — | failed：**57.1 GiB**（§8 那个 bug） |
| 29 | regression | linear_regression | DepDelay | failed（0.39 s，见下） |
| 30 | clustering | kmeans | — | success（silhouette_note 显示已按 §8 抽样到 20 万行） |

三处缺陷叠在一起：

**① `ml.train` 漏传 `infer_target`。** `MlDetectTaskTool` 默认「未指定目标列即聚类」，
只有传 `infer_target=True` 才会按命名约定推断（`target/label/y/class`）。
`MlTrainTool` 的注释声称会传，**代码里没传** ⇒ 「训练一个模型」静默变成聚类。

**② 名称已经写明任务类型，却没人看。** 数据集叫「航空公司出发延误预测（回归）」，
但没有一列叫 `target/label/y/class`，于是 `DepDelay`（延误分钟，本该是目标列）
降级成普通特征。名称里的「回归 / 分类 / 聚类」（含英文 `regression` 等）
是一个零成本、高置信的信号。

**③ 目标列被写进 `excluded_columns` 直接报错。** 目标列本来就不参与特征
（`X = df.drop([target])`），所以「把 target 也列进排除列」是一条**幂等的冗余指令**。
原实现在 `ExperimentService._execute` 与 `ml_engine/step_runner.run_load_step`
两处都直接抛异常 ⇒ experiment 26/27/29 在 0.2 秒内必然失败，用户只看到
「训练失败」四个字，模型链路整条没跑起来。

修复后（实测，dataset 9 全量 1000 万行，无 LLM）：

```
ml.detect_task(infer_target=true)  → 失败，但给出可用信息：
  未指定目标列且无命名约定候选
  而数据集名称提示这是回归任务，不能默认按聚类处理
  回归候选：['DepDelay', 'CRSDepTime', 'CRSArrTime', 'Distance']
  分类候选：['Month', 'DayofMonth', 'DayOfWeek', 'UniqueCarrier']

ml.train(target='DepDelay', model='auto', excluded_columns=['DepDelay','Origin','Dest'])
  → success：linear_regression（model_adjusted from auto）
    excluded_columns 自动裁成 ['Origin','Dest']（目标列被剔除，不再报错）
    sampling: 10,000,000 → 200,000 行（sample_rate 0.02，§8 的抽样回执）
    train/test = 160000 / 40000
    metrics: r2=0.0183, rmse=28.69, mae=14.28
```

另外把「换模型时残留任务专属超参数」一并修掉：任务被推断为分类后，模型
从 kmeans 换成 logistic_regression，而 `params` 里的 `n_clusters` 被一起带过去，
sklearn 报 `LogisticRegression.__init__() got an unexpected keyword argument
'n_clusters'` —— 报错文本完全看不出是「换了模型」引起的。
现在按 `MODEL_PARAMS` 裁剪并记入 `model_adjusted.dropped_params`。

规则规划器也修了一处：`model = "linear_regression" if "回归" in 请求 else
"logistic_regression"` —— 用户说「选择适合的模型」时请求里既没有「回归」也
没有「分类」，于是硬给了 logistic_regression，再被静默换成 kmeans。
现在无明确算法要求时统一给 `auto`。

## 11. 目标列推断死锁的破解（第三轮事故复盘）

### 11.1 现象

§10 修完之后，事故并没有结束 —— 只是**换了一种形式**：

```
ml.detect_task  失败
未能按命名约定确定目标列，而数据集名称提示这是回归任务，不能默认按聚类处理。
请显式指定 target 后重试；
回归候选：['DepDelay', 'CRSDepTime', 'CRSArrTime', 'Distance']
分类候选：['Month', 'DayofMonth', 'DayOfWeek', 'UniqueCarrier']
```

这一条**是 §10.7 自己"修"出来的**：上一轮为了不静默聚类，把「找不到目标列」
改成「明确失败并回传候选」。方向没错，但它把链路**死锁**了：

| 角色 | 知道什么 | 缺什么 |
| --- | --- | --- |
| 规划器（LLM） | 用户诉求 | **看不到列名**（`ContextBuilder` 禁止规划阶段读 Schema）⇒ 填不出 target |
| `ml.detect_task` | 列名 / 类型 / 分布 | 拿不到用户诉求 ⇒ 只能列候选 |
| 用户 | 想预测「延误」 | 不在执行回路里 |

提示词里写着「若回传 needs_target 就从 target_candidates 里选」，
但规划器**在规划阶段根本还没看到候选**（那是执行期才产生的）。
三方各缺一块 ⇒ 没有任何一方能做出决定。

> **判定法**：遇到「工具报缺参数、但每个调用方都说自己没有这个信息」，
> 不是某处写错，而是**架构缺一条数据通路**。加校验、加报错只会把死锁
> 变成"显式失败"，真正要做的是把那条通路补上。

### 11.2 修法：分级证据 + 永远给理由

新增 `backend/app/ml_engine/target_inference.py`（纯逻辑，无 DB 依赖）：

| 级别 | 证据 | confidence |
| --- | --- | --- |
| ① | `explicit` —— 调用方显式指定 | 1.00 |
| ② | `naming_convention` —— `target`/`label`/`y`/`class`/`*_target` | 0.95 |
| ③ | `goal_match` —— 诉求与**数据集名称**的语义匹配 | 0.85 |
| ④ | `single_candidate` —— 排除日历/时间/标识列后唯一 | 0.60 |

四条关键设计（每条都对应一个具体的坑）：

1. **诉求不能只靠 LLM 传参**。`ToolExecutionContext.extra["user_request"]` 由
   `AgentRuntime._tool_context` 注入，工具取
   `params.get("goal") or context.extra["user_request"]`。
   更稳的一层：把**数据集名称也当意图文本** ——「航空公司出发延误预测」里
   本身就写着预测对象，实测**不传 goal 也能推对**（0.49 s）。
2. **列名必须分词后匹配，不能子串匹配**：`age` 子串会命中 `average`。
   英文别名要求词元级相等，长度 ≥ 4 才允许前后缀（`delay` 命中 `depdelay`）；
   中文别名用子串（`流失` 命中 `是否流失`）。
3. **语义命中优先于启发式排除**：`ResponseTime` 会被「时间分量」规则排除，
   但只要诉求里出现「响应时间」，语义命中直接胜出。排除规则只在兜底生效。
4. **歧义不猜，且"有冲突证据"时禁止兜底**。写测试时才发现这条：
   数据集说是回归、诉求命中 `delay_flag`（二元列）时，若继续走「唯一候选」兜底，
   会选中语义完全无关的 `distance` —— **把「预测延误」悄悄换成「预测距离」，
   比失败危险得多**。所以：只要语义有命中但与任务类型不符，立即停止并交还调用方。
   兜底通道**仅在完全没有语义证据时启用**。

同时删掉了 `ml.train` 里那份重复的「预检」：它比 `detect_task` 少一层语义推断，
于是同一件事出现两条不同口径的报错（§10 里两处消息不一致的根源）。

### 11.3 顺带修掉的真实缺陷：回归任务被按类别分层切分

`_can_stratify(y)` 只看目标唯一值数，**不看任务类型**，而它的调用点在
「非聚类」分支里（含回归）。于是「延误分钟被取整成几十档」这种
**低基数回归目标**被当成多分类：

```
测试集样本不足以覆盖 70 个类别（当前 200 行、test_size=0.2，仅能划分 40 个测试样本）
```

一次完全正常的回归训练被判死，而且报错**把回归说成分类**，排查方向完全错。

修法：`experiments/service.py` 与 `ml_engine/step_runner.py` 两处统一改为

```python
stratify = (task == "classification") and _can_stratify(y)
```

> **教训**：任何「按目标取值数」做的判定，都必须先问任务类型。
> 分层切分是纯分类技术，回归用它没有任何统计意义。

### 11.4 实测（dataset 9，10,000,000 行 × 10 列）

```
# ① 事故那一行原样复现 —— 现在成功
ml.detect_task(dataset_id=9, infer_target=true)          → 0.49 s
  task=regression  target=DepDelay
  target_source=goal_match  target_confidence=0.85
  reasons: ['数据集名称提示这是回归任务',
            '未命中目标列命名约定（target/label/y/class 等）',
            '诉求/数据集名称中识别到预测对象语义：delay',
            '语义命中的列中，唯一与回归任务相符的是 DepDelay',
            '据此选定目标列 DepDelay（依据 goal_match，置信度 0.85）']

# ② 不指定 target 直接训练 —— 现在能跑通
ml.train(dataset_id=9, model="auto")                     → 3.09 s, exp 32
  model_adjusted = {from: auto, to: linear_regression, task: regression}
  target_inferred = {target: DepDelay, source: goal_match, confidence: 0.85, ...}
  metrics = {r2: 0.0225, rmse: 29.30, mae: 14.19}
  artifacts: stratified=False, sampling 10,000,000 → 200,000 (rate 0.02)
  exp.target_column = 'DepDelay'
  exp.description   = '[目标列 DepDelay 由推断得出：依据 goal_match，置信度 0.85；…]'
```

推断结论三重回执：**工具结果**（`target_inferred` 含理由）、**实验描述**（落库）、
**报告**（§10 的 `discover_ml_context` 会带上）。缺失会显式说明，静默替用户决定
的路径已经封死。
