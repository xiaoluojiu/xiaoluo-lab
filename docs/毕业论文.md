# 小洛实验室：智能数据科学实验平台的设计与实现

## 摘 要

随着数据科学在各行业的深入应用，数据处理、分析与建模逐渐成为高校实验教学与科研工作中的常态化需求。然而，传统的数据分析流程存在工具链割裂、操作门槛高、结果不可复现、缺乏统一平台支撑等痛点：使用者往往需要在不同的工具之间反复切换，难以将「数据清洗—探索分析—特征建模—结果报告」完整链路沉淀到同一套可追溯、可复现的体系之中。与此同时，大语言模型（LLM）的兴起为数据分析的智能化、自然语言化交互提供了新的可能，但如何让模型能力安全、可控地接入数据分析流程，仍是一个具有现实意义的问题。

针对上述问题，本文设计并实现了一个本地优先、可服务器部署的智能数据科学实验平台——小洛实验室（XiaoLuo Lab）。该平台将数据处理、智能数据合并、探索性分析（EDA）、机器学习建模、Agent 智能分析、工作流编排与实验报告生成等能力整合于一体，并系统性地贯彻了本地化存储、可复现实验、安全可控 AI 编排三项设计原则。

在技术实现上，平台采用前后端分离架构：后端基于 FastAPI 与 Polars/PyArrow 列式计算引擎，构建了以「不可变版本快照」为核心不变量的数据引擎，并实现了由上下文构建、计划生成、权限裁决、工具执行、结果校验与失败重规划六阶段组成的 Agent 编排系统；前端基于 React 与 TypeScript，提供了涵盖数据管理、探索分析、建模实验、AI 对话与工作流编排的完整交互界面。系统内置 30 个 Agent 工具、11 个机器学习模型与 9 类可视化图表，支持中文实验报告的自动生成与多格式导出，并通过工具注册表、权限裁决与 Token 预算记账保障了智能分析的执行安全与成本可控。

测试结果表明，平台共通过 509 项自动化测试用例，静态代码检查清洁，前端类型检查零错误，能够稳定支撑从数据上传到报告导出的完整实验链路。本文最后对系统的安全性、可扩展性进行了分析，并讨论了后续在交叉验证、异步训练与多租户安全等方面的优化方向。

**关键词**：数据科学平台；FastAPI；Polars；机器学习；智能体；工作流编排；可复现实验

## Abstract

With the deepening application of data science across industries, data processing, analysis, and modeling have gradually become routine requirements in university experimental teaching and scientific research. However, traditional data analysis workflows suffer from fragmented toolchains, high operational barriers, non-reproducible results, and the lack of a unified platform. Users often need to switch repeatedly between different tools, making it difficult to consolidate the complete chain of "data cleaning—exploratory analysis—feature modeling—result reporting" into a traceable and reproducible system. Meanwhile, the rise of large language models (LLMs) offers new possibilities for intelligent and natural-language interaction in data analysis, yet how to integrate model capabilities into the analysis workflow safely and controllably remains a practically significant problem.

To address the above issues, this thesis designs and implements a local-first, server-deployable intelligent data science experiment platform — XiaoLuo Lab. The platform integrates data processing, intelligent data merging, exploratory data analysis (EDA), machine learning modeling, agent-based intelligent analysis, workflow orchestration, and experiment report generation into a unified system, systematically implementing three design principles: local storage, reproducible experiments, and secure and controllable AI orchestration.

Technically, the platform adopts a front-end/back-end separated architecture. The back-end is built on FastAPI and the Polars/PyArrow columnar computation engine, constructing a data engine centered on the core invariant of "immutable version snapshots," and implementing a six-stage agent orchestration system consisting of context building, plan generation, permission arbitration, tool execution, result validation, and failure re-planning. The front-end, built on React and TypeScript, provides a complete interactive interface covering data management, exploratory analysis, modeling experiments, AI dialogue, and workflow orchestration. The system integrates 30 agent tools, 11 machine learning models, and 9 types of visualization charts, supporting automatic generation and multi-format export of Chinese experiment reports, while the tool registry, permission arbitration, and token budgeting mechanisms ensure execution safety and cost controllability of intelligent analysis.

Testing results show that the platform passes 509 automated test cases, passes static code checking cleanly, and achieves zero errors in front-end type checking, reliably supporting the complete experiment chain from data upload to report export. Finally, this thesis analyzes the system's security and scalability, and discusses optimization directions in cross-validation, asynchronous training, and multi-tenant security.

**Keywords**: Data Science Platform; FastAPI; Polars; Machine Learning; Agent; Workflow Orchestration; Reproducible Experiments

# 第 1 章 绪论

## 1.1 研究背景与意义

### 1.1.1 数据科学实践的现状与痛点

进入大数据时代，数据已成为重要的生产要素。无论是在高校的数据科学课程、科研课题，还是在企业的实际业务中，数据分析与建模都是一项高频且基础的工作。然而，一个完整的数据科学工作流通常包含数据采集、数据清洗、探索性分析（EDA）、特征工程、模型训练与评估、结果呈现与报告等多个环节。在实际操作中，这些环节往往面临以下突出问题：

第一，**工具链割裂**。使用者需要借助多种工具（如 Python 脚本、Jupyter Notebook、Excel、各类可视化工具、报告编辑软件等）来完成一条完整链路，数据在不同工具之间的迁移不仅繁琐，还容易引入格式不一致、口径不统一等问题。

第二，**操作门槛高**。传统的数据处理与分析依赖编程能力，对于非计算机专业的用户（如经管、医学、社会科学等领域的研究者与本科生）而言，掌握 pandas、scikit-learn 等库并正确完成数据清洗与建模，存在较高的学习成本。

第三，**结果不可复现**。数据分析过程往往是一次性的、非结构化的，缺乏对数据版本、模型参数、随机种子等关键要素的规范记录，导致同一实验难以被他人复现或自我追溯，这既不利于科研诚信，也不利于实验教学的考核与复盘。

第四，**缺乏统一平台支撑**。数据、模型、报告分散存储于个人电脑的各个角落，缺乏统一的组织、检索与共享机制，难以形成可持续积累的实验资产。

### 1.1.2 大语言模型带来的新机遇与新挑战

近年来，以 GPT、DeepSeek 等为代表的大语言模型（Large Language Models, LLMs）展现出了强大的自然语言理解与生成能力。将 LLM 引入数据分析领域，有望实现"用自然语言驱动数据分析"的智能化交互——用户只需描述需求，系统即可自动规划并调用相应的数据处理、分析、建模工具完成任务。这一方向极大地降低了数据分析的使用门槛。

然而，LLM 的引入也带来了新的挑战：其一，LLM 的"自由行动"能力若不加约束，可能执行危险操作（如执行任意代码、删除数据）；其二，LLM 的调用成本（Token 消耗）需要被精细地预算与记录；其三，LLM 可能陷入无效的反复尝试（死循环）。因此，如何构建一个**安全、可控、可预算**的 Agent 编排机制，是当前数据分析智能化研究中的一个关键问题。

### 1.1.3 本课题的意义

基于上述背景，本文设计并实现了一个本地优先、可服务器部署的智能数据科学实验平台——小洛实验室。该平台的实践意义体现在三个层面：

从**工程价值**看，平台将数据处理、智能合并、EDA、机器学习、Agent 分析、工作流与报告生成整合于一体，填补了"从数据到报告"完整链路的平台化空白，具有直接的可用性。

从**学术价值**看，平台在 Agent 编排的安全性设计（权限裁决、无 shell/eval/exec 通道、死循环防线、Token 预算）、可复现实验机制（不可变版本快照 + 随机种子）等方面进行了系统性的工程探索，为"LLM 驱动的数据分析"这一方向提供了可参考的实现范式。

从**教学价值**看，平台面向高校毕业设计与数据科学实验教学，通过中文报告自动生成、实验对比、可追溯分析等功能，为学生提供了一条从数据理解到成果产出的标准化路径。

## 1.2 国内外研究现状

### 1.2.1 数据分析平台的发展

在数据科学工具领域，国内外已有诸多成熟方案。国外方面，Jupyter 生态（Jupyter Notebook / JupyterLab）以其交互式编程能力成为数据科学的事实标准之一，但需要用户具备编程能力；Tableau、Power BI 等商业 BI 工具提供了强大的可视化与拖拽式分析能力，但更侧重于报表展示，对机器学习建模与可复现实验的支持较弱。国内方面，阿里云 DataWorks、字节跳动 DataFinder 等平台面向企业级数据治理与业务分析，功能全面但部署复杂、偏向企业场景，不适合轻量化的教学与个人实验场景。

### 1.2.2 机器学习平台与 AutoML

在自动化机器学习（AutoML）领域，出现了 H2O、AutoGluon、TPOT 等代表性工具，它们能在一定程度上自动完成特征工程与模型选择。然而，这些工具多以库或命令行形式存在，缺乏与数据处理、报告生成等环节的深度整合，且其"黑盒"式的自动化对教学场景下的原理讲解并不友好。

### 1.2.3 LLM 驱动的数据分析

随着大语言模型的兴起，出现了 ChatGPT Code Interpreter、GitHub Copilot、以及各类"AI 数据分析助手"等产品。它们通过自然语言理解用户的意图，并生成代码或调用工具来执行分析。这一方向极具前景，但普遍面临**执行安全性**（如何防止模型执行危险操作）、**结果可信性**（如何校验模型输出的正确性）与**成本可控性**（如何预算 Token 消耗）三大问题。小洛实验室在 Agent 编排层的设计中，正是针对这三个问题给出了系统性的工程方案。

### 1.2.4 现有工作的不足与本课题的切入点

综合来看，现有工作存在以下不足：一是工具链割裂，缺少将完整链路一体化的轻量平台；二是可复现性支持不足；三是 LLM 接入的安全性与可控性缺乏系统设计。本课题的切入点正是：**以一个统一平台承载完整数据科学链路，以不可变版本快照与随机种子保证可复现，以权限裁决 + 工具注册表 + 预算记账保证 AI 编排的安全可控**。

## 1.3 主要研究内容

本文的主要研究内容与工作包括：

1. **需求分析**：调研数据科学实验场景的典型需求，抽象出平台的功能需求与非功能需求，并给出用例模型。

4. **分析模块设计与实现**：实现数据画像、数据质量检查与探索性分析，支持九类可视化图表，并对性能瓶颈进行批量化与缓存优化。

6. **Agent 智能分析系统设计与实现**：构建六阶段 Agent 编排链路，实现 30 个内置工具、权限裁决、结果校验、失败重规划与 Token 预算记账，并完成 SSE 流式交互与授权确认闭环。

7. **工作流与报告子系统**：实现 DAG 工作流引擎与中文实验报告自动生成（Markdown/HTML/PDF 三格式）。

8. **系统测试**：通过单元测试、集成测试与端到端黑盒测试，验证系统的功能正确性、可复现性与安全性。

# 第 2 章 相关技术综述

## 2.1 后端开发技术

### 2.1.1 FastAPI

FastAPI 是一个基于 Python 的高性能 Web 框架，构建于 Starlette（异步 Web 框架）与 Pydantic（数据校验库）之上。它具有以下特点：一是性能优异，接近 Node.js 与 Go 的吞吐水平；二是基于 Python 类型注解的自动数据校验与序列化，显著减少样板代码；三是自动生成交互式 API 文档（OpenAPI / Swagger UI），便于前后端协作与接口调试；四是原生支持异步编程与依赖注入。本系统选用 FastAPI 作为后端框架，统一了异常处理、参数校验与响应包装，并通过中间件实现了请求上下文管理与统一异常兜底。

### 2.1.2 Pydantic 与 SQLAlchemy

Pydantic v2 是 Python 的数据校验与序列化库，用于定义请求体与响应体的数据模型（Schema），实现自动类型校验。SQLAlchemy 2.0 是 Python 的 ORM（对象关系映射）框架，用于以面向对象的方式操作数据库。本系统采用 Pydantic 定义出入参 Schema、SQLAlchemy 定义 ORM 模型、Alembic 管理数据库迁移，三者协同构成后端的数据访问层。

### 2.1.3 Polars 与 PyArrow

Polars 是一个高性能的 DataFrame 库，采用列式存储与惰性执行（Lazy Execution）策略，通过查询优化器将多个操作合并执行，在处理大规模数据时性能显著优于基于行式存储的传统方案。PyArrow 是 Apache Arrow 的 Python 实现，提供了统一的列式内存格式与 Parquet 文件的高效读写能力。本系统选用 Polars 作为领域层的通用数据协议（`pl.DataFrame`），以 Parquet 作为数据集版本快照的存储格式，兼顾了计算性能与存储效率。

## 2.2 机器学习技术

### 2.2.1 scikit-learn

scikit-learn 是 Python 生态中最广泛使用的机器学习库，提供了丰富的监督学习（分类、回归）、无监督学习（聚类、降维）算法，以及统一的 `fit`/`predict` 接口、预处理工具（`ColumnTransformer`、`Pipeline`）与评估指标。本系统基于 scikit-learn 构建了统一的模型适配器（ModelAdapter）与预处理管道（PreprocessingPipeline），实现了分类、回归、聚类、降维四类共 11 个模型的统一训练、预测与评估。

### 2.2.2 数据泄漏防护

数据泄漏（Data Leakage）指在模型训练过程中，测试集信息被不当地泄漏到训练过程，导致评估结果虚高。常见的泄漏来源包括在划分训练/测试集之前进行标准化、用全体数据的统计量填补缺失值等。本系统通过 sklearn `Pipeline` 与 `ColumnTransformer`，确保所有预处理统计量仅在训练集上拟合（`fit_transform`），在测试集上仅做变换（`transform`），从机制上避免了数据泄漏。

## 2.3 大语言模型与 Agent 技术

### 2.3.1 大语言模型与 OpenAI 兼容协议

大语言模型（LLM）是基于海量语料预训练的生成式模型，能够理解自然语言并生成连贯文本。OpenAI 兼容协议（OpenAI-Compatible API）是一种事实上的接口标准，众多模型服务商（如 OpenAI、DeepSeek 等）均提供兼容该协议的 HTTP 接口。本系统通过 httpx 直接对接兼容协议，**不绑定任何具体厂商**，可通过配置切换任意兼容服务，具备良好的可移植性。

### 2.3.2 Agent 与工具调用

Agent（智能体）是指能够感知环境、制定计划、执行动作并调整行为的自主系统。在 LLM 语境下，Agent 通常指"由 LLM 作为核心决策器，通过调用外部工具完成任务的系统"。工具调用（Tool Calling）是 Agent 的核心能力，即 LLM 根据任务生成结构化的工具调用请求，由运行时执行后返回结果。本系统的 Agent 即采用"规划—执行—校验—重规划"的编排范式，通过工具注册表统一管理 30 个内置工具。

### 2.3.3 SSE（Server-Sent Events）

SSE 是一种基于 HTTP 的服务器向客户端单向推送事件的技术。与 WebSocket 相比，SSE 实现更简单、更适用于"服务器持续推送、客户端只读"的场景。本系统采用 SSE 实现 Agent 运行过程的实时事件推送（计划生成、工具调用、校验、最终回答），并利用 SSE 长连接实现高风险操作授权确认的等待闭环。

## 2.4 前端开发技术

### 2.4.1 React 与 TypeScript

React 是一个用于构建用户界面的 JavaScript 库，采用组件化与声明式编程范式，配合虚拟 DOM 实现高效渲染。TypeScript 是 JavaScript 的超集，通过静态类型系统提升代码的可维护性与可靠性。本系统前端采用 React 18 + TypeScript 5，通过严格的类型定义保证前后端数据契约的一致性。

### 2.4.2 Vite、Zustand 与 React Router

Vite 是新一代前端构建工具，基于原生 ES 模块实现极快的冷启动与热更新。Zustand 是一个轻量级的状态管理库，以极简的 API 提供全局状态管理。React Router 用于前端路由管理。本系统采用 Vite 作为构建工具、Zustand 管理全局状态（如 AI 实验室会话状态）、React Router 实现路由与代码分割（懒加载）。

### 2.4.3 Recharts

Recharts 是一个基于 React 与 D3 的可视化图表库，提供了折线图、柱状图、散点图、热力图等多种图表组件。本系统前端使用 Recharts 渲染后端返回的可视化数据，实现九类图表的交互式展示。

## 2.5 本章小结

本章介绍了系统实现所依赖的关键技术，包括后端框架 FastAPI、数据校验库 Pydantic、ORM 框架 SQLAlchemy、列式计算引擎 Polars/PyArrow、机器学习库 scikit-learn、大语言模型与 Agent 技术、SSE 协议，以及前端框架 React/TypeScript、构建工具 Vite、状态管理 Zustand 与可视化库 Recharts。这些技术为本系统的实现奠定了坚实基础。

# 第 3 章 需求分析

## 3.1 需求概述

小洛实验室的目标用户是数据科学学习者与实验者（尤其是高校本科生与跨专业研究者）。用户的核心诉求是：**在一个统一的平台上，从一份原始数据出发，经过清洗、探索、建模、分析与总结，最终产出一份可复现、可追溯、可导出的实验报告**。此外，用户希望通过自然语言与系统交互，降低使用门槛。

# 第 4 章 系统总体设计

## 4.1 系统总体架构

### 4.1.1 架构概述

本系统采用**前后端分离**的单体分层架构。前端负责交互与可视化呈现，后端负责业务逻辑、数据计算与存储。前后端通过统一的 RESTful API（前缀 `/api/v1`）通信，Agent 运行过程通过 SSE 协议进行实时事件推送。

【图 4-1 系统总体架构图：请在此处插入系统总体架构图，展示前端（React）、后端（FastAPI 分层）、数据引擎、机器学习、Agent、存储等各层及其关系。】

### 4.1.2 后端分层设计

后端内部进一步划分为五层：

1. **接入层**（`app/main.py` 与 `app/api/v1/*`）：负责 HTTP/SSE 请求接入、参数校验、响应包装，共注册 14 个 Router（datasets、dataset_analysis、files、processing、merge、eda、experiments、ml_router、workflow、agent、reports、settings、learning、notifications）。
2. **依赖装配层**（`app/api/deps.py`）：负责依赖注入与进程级单例管理。
3. **服务层**（`services/`、`data_engine/service.py`、`experiments/service.py`、`workflow/service.py`、`agent/runtime/*`）：领域门面，对外提供统一业务能力。
4. **领域能力层**（`analysis.py`、`ml_engine/*`、`reports/*`、`tools/*`、`workflow/*`）：实现具体的领域逻辑。
5. **数据访问/基础设施层**（`models/*`、`storage/*`、`core/*`）：数据库 ORM、对象存储抽象、配置、日志、异常。

分层的核心约束是**依赖方向自上而下**：领域能力层不得依赖 FastAPI 等接入层技术，以保证领域逻辑的可测试性与可移植性。

### 4.1.3 前端架构设计

前端采用组件化设计，按职责划分为：

- **页面层**（`pages/`）：路由对应的页面容器。
- **功能组件层**（`features/`）：与具体业务强绑定的组件（如 ChatPanel、DistributionChart、MergePanel）。
- **通用组件层**（`components/`）：跨业务复用的组件（如 DataTable、ConfirmDialog、Loading）。
- **状态管理层**（`store/`）：基于 Zustand 的全局状态。
- **数据访问层**（`api/`）：基于 axios 的后端 API 封装。

前端路由采用 React Router 并配合懒加载（`React.lazy`）实现代码分割，降低首屏加载体积。

## 4.2 核心设计原则与不变量

系统的正确性与可维护性依赖于一组贯穿始终的设计原则与不变量，它们是理解整个系统的"钥匙"：

### 4.2.1 不可变版本快照（核心不变量）

**任何数据修改一律产生新版本（新行 + 新 Parquet 文件），原版本永不覆盖。** `DatasetVersion` 模型不提供 update 方法，Repository 层禁止更新版本数据内容。这一不变式带来三重收益：

1. **可追溯**：完整保留数据演变历史，任何时刻都可回看历史版本。
2. **可复现**：实验绑定具体的版本快照，而非"当前最新数据"，保证实验结果可复现。
3. **可缓存**：版本不可变，意味着版本级 DataFrame 缓存永不失效，只需 LRU 淘汰，无需考虑缓存一致性。

### 4.2.2 领域层与接入层分离

领域能力层（数据引擎、ML 引擎、分析模块）不得依赖 FastAPI，仅依赖纯计算库（Polars、scikit-learn 等）与公共工具。这保证了领域逻辑可以被单元测试直接覆盖，也降低了框架替换的迁移成本。

### 4.2.3 AI 编排安全可控

Agent 系统的三条安全底线：一是**无执行通道**（无 shell/eval/exec），所有能力都通过受控的工具注册表提供；二是**权限裁决前置**（高风险工具执行前必须经过权限判定）；三是**预算与循环约束**（Token 预算记账 + 步数/事件数/重规划次数三重硬限制）。

### 4.2.4 统一异常处理体系

系统定义了以 `AppException` 为基类的 8 类业务异常（`ValidationException`、`NotFoundException`、`PermissionDeniedException`、`DatasetException`、`StorageException`、`WorkflowException`、`AgentException`、`ToolExecutionException`），每类异常绑定明确的 HTTP 状态码与错误码。所有异常由 ASGI 中间件统一兜底，转换为结构化的 JSON 响应（code/message/details/request_id），实现业务异常与系统异常的分离，保证前端能获得一致的错误处理体验。

### 4.2.5 进程内状态与单 worker 约束

系统的 Agent 会话存储（`AGENT_STORE`）与工作流服务（`WORKFLOW_SERVICE`）均为进程级单例，其状态保存在进程内存中。这一设计隐含了**单 worker 部署约束**：若采用多 worker（`uvicorn --workers > 1`），Agent 的 SSE 流与授权确认、工作流的运行与取消可能落到不同进程而静默失效。该约束在系统设计上被明确记录，为后续向 Redis/数据库外置状态演进预留了空间。

# 第 5 章 系统详细设计与实现

## 5.1 数据引擎的设计与实现

### 5.1.1 多格式数据加载

数据加载通过 `data_engine/loaders.py` 中的 `REGISTRY` 实现。加载器按文件扩展名自动匹配，支持 CSV、Excel（.xlsx）、JSON、Parquet 四种格式，统一返回 Polars 的 `DataFrame`。加载器采用注册表模式，新增格式只需注册对应加载器，无需修改调用方代码。

### 5.1.2 九类数据操作

数据操作通过 `OPERATION_REGISTRY` 调度，操作类型包括：缺失值处理（`missing`）、去重（`duplicate`）、类型转换（`cast`）、字符串操作（`string`）、过滤（`filter`）、派生列（`transform`）、分组聚合（`aggregate`）、透视（`pivot`）、融化（`melt`）。所有操作均为**纯函数**（`df, **kwargs -> df`），返回新的 DataFrame，遵循不可变语义。新增操作只需在注册表中登记 `op_type -> (func, param_names)`，业务代码通过 `DataEngineService.apply_operation` 调用，无需 if/else 分支。

其中，过滤操作采用**安全 DSL**：只允许白名单算子（等于、不等于、大于、大于等于、小于、小于等于、包含、在集合中、为空）与 and/or 逻辑组合，从源头杜绝了 eval/exec 代码注入的风险。

### 5.1.3 版本化管理

版本管理由 `DatasetService` 承担。每次数据操作成功后，系统将新的 DataFrame 写入 Parquet 文件（`data/datasets/<id>/v00000N.parquet`），创建新的 `DatasetVersion` 记录，并记录 `Operation` 审计行。版本号单调递增，原版本文件永不删除或覆盖。

### 5.1.4 版本级缓存

由于 `DatasetVersion` 不可变，系统引入了版本级 DataFrame LRU 缓存（`data_engine/cache.py`），以 `(dataset_id, version)` 为键缓存 DataFrame，并设 `max_items` 与 `max_bytes` 双上限。缓存命中时返回 `clone()` 避免调用方原地修改污染缓存。该缓存将一轮 EDA 浏览对同一份 Parquet 的解码次数从 8~10 次降为 1 次。

### 5.1.5 存储安全（路径穿越防护）

数据存储层（`storage/security.py`）实施了严格的路径安全校验，确保任何存储操作都不能逃逸存储根目录（`DATA_ROOT`）。具体检查项包括：路径穿越（`..`/`..\`）、绝对路径与盘符、符号链接逃逸（解析后必须仍在根目录内）、Windows 保留设备名（con/prn/aux 等）与非法字符。所有存储 key 在写入前都经过规范化与校验，从源头上杜绝了通过文件名注入实现路径穿越攻击的风险。

## 5.2 智能合并的设计与实现

### 5.2.1 四段分离设计

智能合并将"把两个数据集按 Join Key 关联为新版本"这一过程严格拆分为四个独立阶段，各阶段职责单一：

1. **字段映射建议**（`schema_mapper.suggest_mappings`）：比较两侧字段的名称、类型、样本值、唯一性、缺失率，输出带置信度的映射候选。
2. **Join Key 分析**（`key_analyzer.analyze_join_keys`）：分析两侧 Key 的唯一性、重复、空值、覆盖率与连接基数（一对一/一对多/多对一/多对多），支持单 Key 与复合键（composite key）。
3. **合并预览**（`MergeExecutor.preview`）：在内存中执行 join，返回输入/输出行列数、匹配信息、警告与冲突，但不创建版本、不写操作记录。
4. **校验与执行**（`validator.validate_merge_plan` + `MergeExecutor.execute`）：执行前强制校验 Key 存在性、类型兼容、空值、多对多、字段冲突与数据量风险；执行时写入左数据集的新版本。

### 5.2.2 版本固定机制

为防止"预览用 v1、执行却跑到 v2"的错位，预览返回值携带 `left_version`/`right_version`，执行时必须原样回传，后端校验版本号存在，缺省即拒绝（422）。这一设计保证了预览所见即执行所得。

### 5.2.3 冲突列处理

当两侧存在同名列时，冲突列依次尝试 `_<suffix>`、`_<suffix>_2`、`_<suffix>_3` 等命名，保证输出列名唯一；映射列统一重命名为 `output_column`。

## 5.3 分析模块的设计与实现

### 5.3.1 统一只读分析层

分析模块（`analysis.py`）将原 Profiling、Quality、EDA 三个子模块合并为统一的只读分析层，对外提供四类能力：Schema 分析、数据画像、数据质量检查、探索性分析。所有分析操作**只读、不修改数据、不产生新版本**。

### 5.3.2 数据画像与质量检查

数据画像（`profile`）按数值/时间/布尔/类别四类列分别输出统计摘要：数值列含 min/max/mean/median/std/分位数，类别列含唯一值计数与高频值。质量检查通过四个 Checker 实现——`MissingChecker`（缺失值）、`DuplicateChecker`（重复行）、`OutlierChecker`（异常值，IQR + Z-score 双方法）、`SchemaChecker`（Schema 一致性），并按 info/low/medium/high/critical 五档严重级别输出报告。质量检查遵循"只发现问题，绝不自动修改数据"的原则。

### 5.3.3 探索性分析与可视化

EDA 提供描述统计、分布分析、相关性分析、异常值分析四个分析器，并支撑九类图表的数据构造。其中两个实现亮点：

- **相关性方法的自动选择**：整数列采用 Spearman（适用于计数/序数），浮点列采用 Pearson，异类列统一采用 Spearman 以保证单调性稳健。
- **Q-Q 图的正态分位数逼近**：自研 Acklam 有理逼近算法计算正态分位数（误差约 1.15e-9），在零 scipy 依赖的前提下实现了科研级的正态性检验可视化。

### 5.3.4 性能优化

针对分析模块的性能瓶颈，系统实施了批量化聚合（将逐列 7 次扫描降为 1 次 `select` 批量聚合）、相关性矩阵对称化与抽样上限、列裁剪下推至 Parquet 读取、图表点集降采样等优化，显著提升了大规模数据下的分析性能。

## 5.4 机器学习模块的设计与实现

### 5.4.1 统一模型适配器与注册表

机器学习模块基于 scikit-learn 构建了统一的 `ModelAdapter` 抽象接口（`fit`/`predict`/`predict_proba`/`evaluate`/序列化），并通过 `MODEL_REGISTRY` 注册表管理 11 个内置模型：4 个分类模型（逻辑回归、KNN、决策树、随机森林）、4 个回归模型、2 个聚类模型（KMeans、DBSCAN）、1 个降维模型（PCA）。业务层只面向注册表，不出现 if/else 模型判断，新增模型只需实现适配器并注册。

### 5.4.2 任务自动识别

`ml.detect_task` 根据目标列的类型、基数、缺失率自动推断任务类型（分类/回归/聚类）。当检测到约定命名（target/label/y/class）或整数且唯一值有限的列时判定为分类，整数多值判回归，无明确目标列判聚类。

### 5.4.3 防泄漏预处理管道

`PreprocessingPipeline` 基于 sklearn `ColumnTransformer` + `Pipeline` 组装缺失填补 → 编码 → 缩放的完整流程，按列名（而非位置）对齐。关键设计在于：**所有统计量（如均值、方差）仅在训练集 `fit_transform` 阶段计算，测试集仅做 `transform`**，从机制上杜绝数据泄漏。预处理配置可由数据画像自动生成，也可由用户在前端自定义。

### 5.4.4 训练、评估与可复现

训练前执行 `preflight` 校验（target 存在/非空、分类至少 2 类、回归样本足够、回归目标列取值无变化），非法输入直接抛出业务异常（`MLEngineException`）而非暴露 sklearn 原始异常。具体地，系统在训练前完成多项稳健性处理：

- **目标列空值清理**：若标签列存在空值，训练前按 `is_not_null()` 过滤掉标签缺失的整行，并记录剔除行数，而非让 sklearn 抛出难懂的 "Input contains NaN" 错误。
- **特征排除**：`excluded_columns` 作为独立语义执行真正的列过滤，目标列绝不允许被排除，最终参与训练的列记录在 artifacts 中。
- **可复现机制**：训练时将随机种子注入 `random_state`（通过签名级探测判断模型是否支持该参数，不支持的模型则仅用于数据切分），分类场景在条件满足时采用分层抽样（`stratify`），并预先校验测试集样本是否足以覆盖所有类别，将 sklearn 的英文报错转成可操作的中文提示。
- **切分比例可配置**：`test_size` 支持显式配置，缺省为 0.2。

评估输出统一指标（分类：accuracy/precision/recall/f1/roc_auc；回归：mae/mse/rmse/r2；聚类：silhouette），指标永不返回 NaN/Inf，无值时为 None 并附说明。此外，系统在训练时同时落一份**训练集指标**（`train_metrics`）与类别分布，供前端进行过拟合诊断——判断依据是训练/测试指标的差距，而非单看测试集绝对值。模型与预处理管道序列化后落盘，实现模型持久化与预测加载。

### 5.4.5 决策阈值与推理

系统的推理链路支持**训练后调整决策阈值**（threshold），这是本模块的一个亮点设计：模型负责输出类别概率，阈值负责决定"概率多少算正类"，两者解耦使得调整阈值无需重新训练。系统在训练时预留二分类的阈值取舍曲线（threshold curve），推理时若数据自带标签还会就地扫描一条推理曲线，并返回标签偏移比（label shift ratio）供用户评估换阈值的影响。对于不适用的场景（回归、聚类、多分类、无概率输出的模型），系统会显式报错而非静默忽略，避免用户误以为阈值已生效。

此外，推理必须同时加载预处理管道（pipeline），因为训练特征是 one-hot/标准化后的列，直接把原始列喂给模型会因列不匹配而失败；概率矩阵仅物化需要返回的前若干行，避免大数据集下的内存放大。

### 5.4.6 实验管理与对比

`ExperimentService` 负责实验的创建、运行、预测、解释与对比。一次实验绑定数据版本快照 + 模型 + 参数 + 预处理 + 种子，保证可复现；`ExperimentComparator` 对比多个运行（Run）的指标差异。模型解释优先复用训练时落库的特征重要性，避免重复计算。

## 5.5 Agent 智能分析系统的设计与实现

### 5.5.1 六阶段编排链路

Agent 系统是本平台的智能化核心，其运行链路分为六个阶段：

1. **上下文构建（ContextBuilder）**：基于用户请求、会话绑定的数据集、历史消息构建受控上下文。关键设计是**上下文层只提供低成本元数据、权限与候选工具，绝不读取 DataFrame、Schema、画像或样本数据**——真实数据读取必须经过工具调用 DataEngine 完成，以便可观测、可审计并控制 Token。数据集信息仅包含名称、描述、版本号、行列数等数据库元信息，且所有上下文字段都受字符上限截断控制。
2. **计划生成（AgentPlanner）**：由 LLM 或规则规划器生成执行计划（`AgentPlan`），计划受 `max_steps` 限制，并支持计划缓存。
3. **权限裁决（PermissionManager）**：根据工具的风险等级与用户角色，判定每次工具调用为允许（ALLOW）、拒绝（DENY）或需确认（REQUIRE_CONFIRMATION）。
4. **工具执行（AgentExecutor）**：通过 `TOOL_REGISTRY.execute` 执行工具，返回结构化的 `ToolResult`。
5. **结果校验（AgentResultValidator）**：校验工具输出的 NaN/Inf、Schema 必需字段与期望输出关键词。
6. **失败重规划（Replanner）**：步骤失败时决定重试/跳过/终止，并受重规划次数硬限制。

### 5.5.2 对话/工具路由

`_route` 根据问候语与数据任务关键词将用户请求分流为"普通对话"与"工具流程"两类。当会话已绑定数据集时，即使关键词未命中，也兜底进入工具流程，避免"数据任务被误当闲聊"。路由判定仅依赖可零成本获得的信号（问候语集合、数据任务关键词、会话是否绑定数据集），不为此读取数据内容。

在计划生成上，系统采用**三级降级**的容错策略：先用候选工具集规划，失败（如 LLM 引用了候选集外的工具）则放开到全量工具集重新规划，再失败则退回规则规划器兜底，保证数据分析请求至少能跑出真实结果，而非因单次规划失败而空手而归。规则规划器内置了数据分析任务的标准交付路径（读取结构 → 数据质量 → 统计画像 → 分布与关系 → 报告生成），确保无 LLM 时也能产出图文并茂的报告。

### 5.5.3 死循环防线（三重保护）

为防止 Agent 陷入无效的反复尝试，系统设置了三重防线：一是**尝试数写回**（每次失败都记录尝试次数，防止单步上限形同虚设）；二是**重试不前进下标**（重试同一步时下标不变）；三是**每次迭代过熔断**（工具调用数/超时/Token 三重熔断）。此外还有 `MAX_EVENTS_PER_RUN=2000` 的事件数硬护栏，宁可让单次运行失败也不拖垮进程。

### 5.5.4 Token 预算记账

系统通过 `TokenLedger` 记录 LLM 的输入/输出 Token 消耗，并通过结果压缩（只将工具结果的摘要喂给 LLM）节省 Token。预算账本通过 `usage` 事件实时推送给前端，让用户直观了解成本。

### 5.5.5 SSE 流式交互与授权确认闭环

Agent 运行支持 SSE 流式推送事件（计划生成、工具调用、校验、回答）。当运行遇到高风险工具时进入 WAITING_CONFIRMATION 状态，SSE 连接保持打开并持续监听，用户在前端确认后调用 `resume` 继续执行，新事件继续经同一条 SSE 推出，实现"点确认不卡死"的交互闭环。

### 5.5.6 工具检索与 30 个内置工具

系统内置 **30 个**工具，按类别组织：

| 类别 | 数量 | 工具 |
| --- | --- | --- |
| 数据集 | 6 | list / inspect / preview / schema / profile / quality |
| 数据 | 5 | filter / clean / transform / aggregate / merge |
| EDA | 5 | describe / distribution / correlation / outlier / visualize |
| 机器学习 | 8 | detect_task / prepare / train / predict / evaluate / compare / explain / explain_config |
| 工作流 | 5 | list / create / inspect / run / build_and_run |
| 报告 | 1 | generate |

所有工具强制走注册表，**没有任何 shell/eval/exec 通道**。

在工具供给策略上，系统采用「本地零 Token 召回 + 确定性注入」的双层机制：`ToolRegistry.retrieve_with_scores` 基于工具名、描述、类别与任务词映射对用户请求做本地打分召回（不消耗 Token），`ContextBuilder.with_tools` 再按请求意图确定性注入一组"能力核心"工具（如 `dataset.inspect`、`report.generate` 等），保证数据分析任务始终能看到关键工具，避免"工具已注册却因未被召回而无法被规划引用"的问题。候选集合最终封顶，防止提示词无限膨胀。

### 5.5.7 本地小模型路由（实验性）

系统预留了本地小模型路由（`local_router/`）的能力，用于在隐私敏感场景下用本地小模型替代远程大模型。该模块支持三档模式：`off`（默认关闭，零风险）、`shadow`（只记录不改变行为，将"本地路由会怎么判"与"线上实际怎么走"并排写入 trace，用于积累数据、验证离线指标）、`guard`（预留档，低置信时交由本地路由决定）。这一设计为平台在"本地优先"定位下的隐私增强提供了演进空间，当前以 shadow 埋点方式低调运行，不干扰主流程。

## 5.6 工作流与报告子系统的实现

### 5.6.1 DAG 工作流引擎

工作流由 `Node`（类型 + 配置）与 `Edge`（源/目标）组成有向无环图（DAG）。执行器采用 Kahn 算法进行拓扑排序后逐节点执行，节点类型采用白名单（noop/data.load/data.clean 等 11 类）。执行语义为：节点失败 → FAILED，后继节点 SKIPPED，其它分支继续执行；支持取消操作。

### 5.6.2 中文实验报告生成

`ReportGenerator` 接收 EDA、ML、质量检查、实验等结构化输入，组织为包含"数据概览、数据质量、探索性分析、建模与评估、结论"五章的中文实验报告。报告支持三种导出格式：Markdown（默认）、HTML、PDF。其中图表采用纯 SVG 渲染（无 matplotlib 依赖），PDF 中文字体路径可配置。

### 5.6.3 LLM 叙述增强

系统通过 `narrator` 模块调用 LLM，基于真实的工具结果撰写报告章节的分析正文，并设置事实摘要截断上限与完整性校验，保证 LLM 输出与真实数据结果一致，避免编造。

# 第 7 章 总结与展望

## 7.1 工作总结

本文围绕"构建一个统一、可复现、安全可控的智能数据科学实验平台"这一目标，完成了以下工作：

1. **完成了需求分析**：调研了数据科学实验场景的典型需求，抽象出六大功能模块与四类非功能需求。

2. **设计了系统架构**：确立了前后端分离的整体架构、后端的五层分层，以及"不可变版本快照""领域层与接入层分离""AI 编排安全可控"三项核心设计原则。

3. **实现了数据引擎**：基于 Polars 列式计算引擎，实现了多格式加载、九类操作、智能合并（四段分离 + 版本固定）与版本化管理。

4. **实现了分析模块**：实现了数据画像、质量检查、探索性分析与九类可视化图表，并进行了批量化与缓存等性能优化。

5. **实现了机器学习模块**：基于 scikit-learn 构建了 11 个模型的统一适配器与防泄漏预处理管道，实现了任务识别、训练评估与可复现实验。

6. **实现了 Agent 智能分析系统**：构建了六阶段编排链路、30 个内置工具、权限裁决、结果校验、失败重规划与 Token 预算记账，并实现了 SSE 流式交互与授权确认闭环。

7. **实现了工作流与报告子系统**：实现了 DAG 工作流引擎与中文实验报告的多格式自动生成。

8. **完成了系统测试**：通过 509 个自动化测试用例验证了系统的功能正确性、可复现性与安全性。

## 7.2 主要创新点

本文的主要创新点可归纳为：

1. **以"不可变版本快照"为核心不变量的可复现数据体系**：将数据版本化与实验可复现、缓存优化有机结合，形成了统一的设计底座。

2. **安全可控的 LLM 数据分析编排范式**：通过工具注册表 + 权限裁决 + 无执行通道 + 三重死循环防线 + Token 预算记账，系统性地解决了 LLM 接入数据分析的安全性与可控性问题。

3. **一体化的数据科学链路**：将数据处理、智能合并、EDA、建模、Agent、工作流与报告生成整合于一个轻量、本地优先的平台，填补了工具链割裂的空白。

4. **训练与推理解耦的决策阈值机制**：将"模型输出概率"与"阈值决定正类"解耦，支持训练后调整决策阈值并辅以阈值曲线与标签偏移比分析，无需重新训练即可调整分类决策边界，同时保留训练集/测试集双口径指标以支撑过拟合诊断。

## 7.3 存在的不足

本文的工作仍存在以下不足：

1. **鉴权体系缺失**：系统当前未实现用户认证与授权，多用户部署场景下存在越权访问风险（对象级鉴权缺失，即 IDOR 问题）。

2. **性能与规模化仍有提升空间**：分析模块虽已进行缓存与批量化优化，但训练仍为同步阻塞，大规模数据下的异步执行与进度反馈尚未实现。

3. **模型能力偏基线**：当前仅提供单次训练/测试切分的基线模型，缺少交叉验证、超参搜索与模型漂移检测等高级能力。

4. **预测结果不可导出**：模型预测目前仅返回预览，尚不支持将全量预测结果写回数据集。

## 7.4 未来展望

针对上述不足，后续工作可在以下方向展开：

1. **完善鉴权与多租户**：引入统一鉴权依赖，为实验/运行等资源增加所有权校验，支持多用户安全部署。

2. **异步训练与进度反馈**：将训练执行移出请求线程，配合已有的运行状态机实现异步训练与进度轮询。

3. **增强模型能力**：引入交叉验证、置信区间、超参搜索与 AutoML 雏形，提升建模的自动化与可靠性。

4. **支持全量预测导出**：实现预测结果写回数据集版本的能力，满足批量打标的实际需求。

5. **分析结果持久化与历史对比**：引入分析结果存档，支持跨版本的质量对比，将平台从"一次性工具"升级为"可追溯的分析档案"。

6. **本地小模型路由**：完善本地小模型路由（local_router）的能力，在隐私敏感场景下用本地小模型替代远程大模型，进一步强化"本地优先"的定位。

## 7.5 本章小结

本章对全文工作进行了总结，提炼了主要创新点，分析了存在的不足，并展望了后续的优化方向。总体而言，小洛实验室作为一个面向数据科学实验教学的智能平台，实现了"从数据到报告"完整链路的平台化支撑，在可复现性与 AI 编排安全可控方面进行了有意义的工程探索，具有较好的实用价值与推广前景。
