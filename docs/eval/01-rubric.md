# MMTU-Lab 评分标准（Rubric）

> 适用对象：小洛实验室 AI 实验室模块的 AI 回复（出口为 `app/agent/answer.py` 的 `render_chat` 与 `render`）
> 基准来源：MMTU 25 类表格任务（实例化说明见 `00-dataset-selection.md`）

---

## 1. 总分构成

| 维度 | 满分 | 判定方式 | 判定者 |
|---|---|---|---|
| 准确性 Accuracy | 25 | 确定性：与 gold 比对 / 执行结果比对 | `graders.py`（不调 LLM） |
| 相关性 Relevance | 25 | LLM 评审，四档锚点 | `judge.py` |
| 完整性 Completeness | 25 | LLM 评审，三档锚点 | `judge.py` |
| 格式合规性 Format | 25 | 确定性：检查项加权 | `graders.py`（不调 LLM） |
| **合计** | **100** | | |

**达标线：单用例总分 ≥ 90 分，且未触发任何红线。**

为什么是 90 而不是 60：这是「回复质量」而非「任务通过率」评测。准确性满分但格式不合规（该给的代码块给了散文）在本产品里同样是不可用的回复 —— 用户复制不走。90 分意味着四维里最多只能有一维出现轻微缺口。

---

## 2. 准确性（25 分）

准确性得分 = 25 × 准确率，准确率由 gold 比对得出，**判定口径移植自 MMTU 官方 `evaluators/`**：

| 判定模式 | 适用任务 | 判定规则 | 分值 |
|---|---|---|---|
| `sql_exec` | NL2SQL | 抽 ```sql 代码块，在 SQLite 上**真跑**，结果集与 gold 一致 | 一致 1.0；可执行但结果错 0.35；不可执行 0 |
| `py_exec` | Data-transform-pbe | 执行模型代码（输入 `s`，输出 `result`），与 gold 比对 | 对 1.0；可执行但错 0.3；异常 0 |
| `exact` | Table-QA / 标注类 / 实体匹配类 | 归一化（去空白、全角转半角、大小写）后 gold 出现在回答中 | 命中 1.0，否则 0 |
| `numeric` | 数值类 | 相对容差 rtol=1e-3 | 命中 1.0；误差 ≤10% 给 0.6（区分「方向对」与「完全错」）；否则 0 |
| `yesno` | 事实校验 / 实体匹配 / 连接判定 | 出现明确表态且与 gold 一致；**同时出现正反两种表态记 0** | 1.0 / 0 |
| `set_f1` | Error-Detect / Schema-Matching / semantic-join / Arithmetic-Relationship / Functional-Dependency | 预测集 = 候选全集中出现在回答里的项，与 gold 算 F1 | 25 × F1 |
| `formula` | Formula-prediction-context | 抽 `=` 后表达式，归一化比对 | 完全一致 1.0；包含 gold 0.5；否则 0 |
| `contains` | 边界场景（失败通报 / 指标解读） | gold 字符串出现在回答中 | 1.0 / 0 |

MMTU 官方 `summary_metric` 中 Error-Detect、Schema-Matching、semantic-join、Arithmetic-Relationship、Functional-Dependency、String-Relationship、equi-join-detect 用的就是 **f1**，本基准沿用同一口径 —— 这类任务的「准确性」本身就包含「有没有列全」。

## 3. 相关性（25 分，LLM 评审）

| 档位 | 判定描述 |
|---|---|
| 25 | 完全聚焦所问，没有跑题内容 |
| 18 | 基本聚焦，但夹带少量无关信息（不必要背景说明、客套话） |
| 10 | 部分跑题，回答了别的问题或擅自扩大范围 |
| 0 | 答非所问，或拒绝回答 |

评审约束：参考答案只用于判对错，同义表述不扣分；用户明确要求「只回答 X」时简洁**不扣**完整性分；编造数据两档均记 0。

## 4. 完整性（25 分，LLM 评审）

| 档位 | 判定描述 |
|---|---|
| 25 | 所问每一项都答到，集合类无漏项，关键限定（排序/去重/口径）都体现 |
| 15 | 主体答到但有遗漏（集合类漏项、少答一个被问到的方面） |
| 0 | 严重缺漏 |

## 5. 格式合规性（25 分，确定性）

按用例声明的检查项加权计分：`25 × 通过项权重和 / 全部权重和`。检查项类型：

| 检查项 | 含义 | 来源 |
|---|---|---|
| `code_block(lang)` | 必须出现指定语言的代码块 | MMTU 官方 prompt 模板（"return the code only with the following markdown codeblock format"） |
| `no_prose` | 明令「不要解释」时，代码块外正文 ≤ N 字 | 同上 |
| `max_len` / `min_len` | 长度约束 | 产品侧 300/400 字上限 |
| `no_code_block` | 要求裸值时不得裹代码块 | MMTU 单值类任务 |
| `no_internal_jargon` | 不得出现「事实摘要 / 本次未获取 / 没有执行 / 我目前没有」 | `answer.py` 硬要求 3 |
| `no_fake_claim` | 不得出现「已生成 / 我画了 / 我帮你算 / 已跑完」 | `answer.py` 硬要求 3.1 |
| `first_sentence_positive` | 首句不得以「无法 / 不能 / 还没 / 尚未 / 没有」开头 | `answer.py` 硬要求 5 |
| `no_ending_ask` | 不得以「请告诉我 / 你希望我 / 需要你补充」结尾 | `answer.py` 硬要求 6 |
| `contains_all` / `contains_none` | 必须出现 / 禁止出现的字符串 | 题目要求与项目红线 |

## 6. 红线（一票否决）

命中任一红线，该用例**总分直接记 0 并判定 FAIL**，不论其余维度得多少分：

| 红线 | 含义 | 为何单列 |
|---|---|---|
| 内部口径外泄 | 出现「事实摘要」「本次未获取」等 | 把系统内部缺口甩给用户，是不可接受的回复 |
| 无工具却宣称已执行 | 出现「我画了」「已生成」「已跑完」 | 纯对话路径没有工具结果，宣称已执行=欺骗 |
| 以否定/无法开头 | 首句为「无法/不能/还没」 | 用户第一眼看到「我白问了」，即使后面给了答案 |
| 以反问/索要补充结尾 | 收尾为「请告诉我/需要你补充」 | 把本可由系统定的默认值推回给用户 |

---

## 7. 执行与防漂移约定

1. **准确性与格式绝不交给 LLM 判**——保证今天评 25 分，明天复跑还是 25 分。
2. **评审固定 temperature=0 + 强制 JSON**，避免评审漂移。
3. **禁止通过调整达标线、放宽检查项让用例"达标"**；优化只能改被测代码。
4. 每轮结果落盘到 `docs/eval/results/round_N.json`，含完整回答原文，可复核。

## 8. 已知局限（如实标注）

- MMTU 28K 原始语料在本环境不可下载，题目为按官方规格本地实例化，gold 由程序实跑产生（真值），但**题目分布不等于官方原题分布**。
- 评审模型与被测模型同为 `deepseek-flash`，存在同源偏好；已通过「主观项与客观项分离、客观项占 50 分」降低影响。
- 用例数 33（25 类各 1 条 + 8 条边界），单类样本量小，结论用于**定位缺陷与驱动优化**，不等同于模型能力排名。
