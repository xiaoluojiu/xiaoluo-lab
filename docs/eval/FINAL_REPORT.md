## 一、数据集选型结论

候选：`MMTU`（NeurIPS'25，28,136 题 / 25 类表格任务）与 `FineEnvs/data-agent-harbor-test`（250 题 / 数据分析 Agent 沙箱基准）。
完整对比见 `00-dataset-selection.md`，决定性理由：

| 维度 | MMTU | data-agent-harbor-test |
|---|---|---|
| 能否测「准确性」 | 能（每类一个确定性 evaluator） | 能（grader.py 判 1.0/0.0） |
| 能否测「相关性」 | 能（官方模板明令「只返回被问到的列」） | 弱（单值对错不区分跑偏） |
| 能否测「完整性」 | 能（7 类任务官方指标就是 f1，考核漏项） | **不能**（答案是单个裸值，不存在漏项概念） |
| 能否测「格式合规性」 | 能（每类 prompt 写死输出格式，如「只返回 ```sql 代码块，不要解释」） | **不能**（要求输出裸值，等于没有格式维度） |
| 与项目内核契合 | 表格是平台一等公民；转换/匹配/补缺/错误检测正是平台已有能力 | 契合，但测的是沙箱执行完成度 |
| 本环境可落地 | 可行（仓库可克隆，任务定义与评分逻辑完整可得） | 不可行（需 Docker 沙箱 + 250 份 Kaggle 数据文件，且 HF 域名不可达） |

**选定 MMTU。**

> **数据不可达的处置（必须说明）**：MMTU 的 28K 原始题目托管在 OneDrive / HuggingFace，
> 本环境对 `huggingface.co`、`cdn-lfs.huggingface.co`、`datasets-server.huggingface.co` 均返回 **502**，无法下载原题。
> 因此按官方规格**本地实例化**：25 类任务一类不删、prompt 格式条款沿用官方模板、
> 判定口径移植自官方 `evaluators/`、题目用小表承载且 **gold 由 SQLite/Python 实跑得出**（真值，可复算）。
> 详见 `00-dataset-selection.md` 第 4.1 节。

## 二、评分标准

总分 100 = 准确性 25 + 相关性 25 + 完整性 25 + 格式合规性 25。
**达标线：单用例 ≥ 90 分，且未触发任何红线。** 完整定义见 `01-rubric.md`。

| 维度 | 判定方式 | 判定者 |
|---|---|---|
| 准确性 | gold 比对 / SQL 实跑 / 代码实跑；集合类用 F1 | 确定性脚本（不调 LLM） |
| 相关性 | 四档锚点（25 / 18 / 10 / 0） | LLM 评审 |
| 完整性 | 三档锚点（25 / 15 / 0） | LLM 评审 |
| 格式合规性 | 检查项加权（代码块语言、禁解释、长度、内部口径、首句/结尾约束…） | 确定性脚本（不调 LLM） |

**红线（一票否决，总分记 0）**：内部口径外泄 / 无工具却宣称已执行 / 以否定词开头 / 以反问索要补充结尾。

**防漂移约定**：客观项（50 分）绝不交给 LLM 判；评审固定 temperature=0 + 强制 JSON + 正则兜底；
禁止通过放宽标准让用例"达标"，优化只能改被测代码。

### 4.1 归因说明（重要）

16 轮里出现的失败，**多数根因不在被测代码**，必须分开看，否则结论会被自己的评测误差带偏：

| 类别 | 条数 | 说明 |

这类缺陷不产生失败，而是产生**虚假的通过**，比显性失败更值得警惕。

## 五、对产品代码的实质性修改

全部改动集中在两个文件，均通过 `pytest backend/tests`（**435 项，0 失败 0 错误**）回归验证。

### 5.1 `backend/app/agent/answer.py`

| # | 改动 | 解决的问题 |
|---|---|---|
| 1 | `render_chat()` 新增 `columns` 参数，把真实列名注入 prompt，并要求「问到清单外的列直接说明不存在，不要替他猜一个值」 | 工具路径 `render()` 早有此护栏，对话路径（幻觉高发区）却是裸奔的 |
| 2 | 新增第 8 条硬要求：多数值聚合必须逐项累加复核，计算过程不写进回答 | 数值聚合口径不严谨 |
| 3 | 新增第 9 条硬要求：穷举类问题必须逐对/逐项过一遍，且**每一项必须在所有数据行上都成立** | 集合任务漏项（召回）与编造（精确率）双向失守 |
| 4 | 新增 `_needs_deep_reasoning()`：聚合/穷举类请求切换到 `thinking="enabled"`，max_tokens 600→1200，**temperature 0.4→0.0** | 无推理链导致算不对；高温度导致同一题不同轮答案不同 |

### 5.2 `backend/app/agent/llm.py`

| # | 改动 | 解决的问题 |
|---|---|---|
| 1 | 新增 `with_thinking()`：返回仅 thinking 设置不同的副本（共享 httpx 客户端） | 让「按任务开关推理链」成为可能，而不是全局开或全局关 |
| 2 | `LLMResponse` 新增 `from_reasoning` 字段 | 上层无法区分「拿到的是答案」还是「拿到的是思维链」 |
| 3 | `_request_with_retry()` 空内容判断改为 `(not content or from_reasoning)` | **防护此前形同虚设**：`_parse()` 先把思维链填进 content，导致「关闭 thinking 重试」永远不触发，思维链直接泄漏给用户 |

第 3 项是本轮最有价值的发现——它是一段**写了却从未生效**的防护代码，
而该文件注释里明确警告过它要防止的现象（「用户看到的最终答案就是一段模型的自言自语」）。

## 七、已知局限（如实标注）

1. **题目是本地实例化，非官方原题**：MMTU 28K 语料在本环境不可下载，题目分布不等于官方分布。
   本基准的作用定位是**暴露缺陷、驱动优化**，其分数不能等同于模型在官方 MMTU 上的能力排名。
2. **评审与被测同为 deepseek-flash**，存在同源偏好。已通过「客观项 50 分完全不交给 LLM」降低影响，
   但主观项仍不可完全避免。
3. **单类任务样本量为 1**，集合类任务的方差虽已收敛（连续七轮满分），但样本不足以断言零方差。
   第 13 轮 E05 的长度抖动即为例证：**客观项（准确性 / 格式）虽由确定性脚本判定，
   但回答本身由采样产生，非确定性任务的篇幅 / 措辞仍会波动**。第 14、15、16 轮该抖动自行回落
   （183 / 139 / 128 字），证实其为采样噪声而非系统性偏移。这类抖动不影响达标，
   但说明「满分」应理解为「在当前样本与温度下稳定达标」，而非「输出逐字恒定」。
4. **聚合计算的正确性依赖推理链**：本次是让 LLM 自己算。更彻底的做法是在引擎层把这类请求路由到
   计算引擎（平台已有 duckdb / polars）求值再回填，LLM 只负责表述——那是架构级优化，不在本轮范围内。
5. **自动化迭代已开启**：每 2 小时自动执行一大轮（测试→分析→优化→复测），轮次状态落在
   `docs/eval/state.json`，可持续跟踪分数是否发生回退。
